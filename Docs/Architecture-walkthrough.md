# Как объяснить GalleryApp на защите

Это памятка к реализованным этапам 1–5, включая Core Data и избранное.

## Кто за что отвечает

**Model — данные.** `Photo` описывает одну фотографию: идентификатор, адреса изображений,
описание и автора. Unsplash — внешний сервис фотографий. Он возвращает JSON;
`JSONDecoder` преобразует JSON в структуры Swift.

**View — отображение и действия пользователя.** В UIKit сюда относятся UIViewController,
UICollectionView и ячейки. Наличие UIViewController само по себе не означает архитектуру MVC:
в нашем проекте решения о загрузке страниц находятся в отдельной ViewModel.

**ViewModel — состояние экрана и правила его изменения.** `GalleryViewModel` хранит список,
номер следующей страницы, загрузку и ошибку. Она не импортирует UIKit и не открывает экраны.
`PhotoDetailsViewModel` хранит выбранный индекс и список для перелистывания.

**Coordinator — переходы.** `AppCoordinator` создаёт экраны и передаёт им зависимости.
Он помещает просмотр фото в UINavigationController. Экран галереи только сообщает
о выборе через замыкание `onSelectPhoto`.

**Сервисы — работа с внешними ресурсами.** `UnsplashPhotoService` отправляет запросы,
`ImageLoader` загружает и кеширует картинки. Они передаются через протоколы,
поэтому в тестах их можно заменить управляемыми подменами.

## Что происходит при запуске

1. SceneDelegate создаёт окно и Coordinator.
2. Coordinator создаёт сервис, ViewModel и экран галереи.
3. Экран просит ViewModel загрузить страницу.
4. ViewModel обращается к сервису. URLSession запрашивает 30 фото через async/await.
5. ViewModel сохраняет результат и вызывает onChange; экран обновляет коллекцию.
6. Каждая ячейка просит ImageLoader загрузить картинку по URL из ответа.

`await` позволяет задаче приостановиться в ожидании результата, не блокируя интерфейс.
`@MainActor` упорядочивает доступ к состоянию интерфейса; это не означает, что ожидание сети
блокирует главный поток. Асинхронность сама по себе не делает любой тяжёлый код фоновым.

## Что происходит при нажатии на фото

1. UICollectionView сообщает экрану индекс выбранной ячейки.
2. Экран передаёт список и индекс Coordinator через onSelectPhoto.
3. Coordinator создаёт PhotoDetailsViewModel и экран просмотра, затем вызывает pushViewController.
4. UIPageViewController запрашивает соседние страницы при свайпах.
5. Только завершённый переход обновляет выбранный индекс и заголовок. Отменённый свайп его не меняет.

Фото открывается внутри приложения. Кнопка с именем автора открывает сайт Unsplash отдельно.
Для просмотра используется regular URL, для сетки — small URL. Просмотр получает снимок
списка на момент открытия: изменение галереи не сдвигает индексы уже открытого просмотра.

## Почему фото не путаются при быстрой прокрутке

UICollectionView переиспользует ячейки: одна ячейка последовательно показывает разные фото.
При переиспользовании отменяется старая задача и очищается изображение. Перед установкой
ответа проверяются отмена задачи и id фото. Поэтому поздний ответ не подменяет новое изображение.
Общая загрузка ImageLoader при этом может продолжиться для других потребителей и кеша.

## Почему одна страница не загружается несколько раз одновременно

ViewModel устанавливает isLoading до первого await. Следующий вызов видит этот флаг
и не запускает второй запрос. Номер страницы увеличивается только после успеха.
Ошибка сохраняет уже показанные фото; кнопка повтора запрашивает неудавшуюся страницу снова.

## Кеш, ключ и база данных — разные вещи

- NSCache хранит подготовленные UIImage в памяти; система может освободить их.
- URLCache хранит HTTP-ответы с учётом правил сервера. Он не гарантирует офлайн-доступность.
- Secrets.plist — локальный файл настройки Access Key, исключённый из Git. Это не база данных.
- Core Data хранит выбранное пользователем избранное между запусками; в нашем приложении данные лежат в SQLite-файле.

Исключение ключа из Git защищает историю репозитория, но ключ из установленного приложения
можно извлечь. Ограничения учебного прямого подключения описаны в Unsplash-setup.md.

## Что доказывают тесты

Подменный сервис возвращает заранее выбранный ответ или ошибку. Так тесты проверяют,
какую страницу запросила ViewModel, сохранила ли старые фото и не допустила ли второй запрос.
Тест просмотра проверяет выбранный индекс и границы списка. Тест экрана проверяет,
что выбор ячейки передаётся обработчику просмотра, а внешняя ссылка не открывается.

Эти проверки не заменяют ручную проверку настоящего свайпа, ориентации и внешнего вида.

## Как работает сердечко

1. Ячейка или экран просмотра сообщает ViewModel о нажатии.
2. ViewModel обращается к общему FavouritesStore.
3. Store просит FavouritesRepository записать или удалить фото через Core Data.
4. Только после успешного save Store обновляет список и уведомляет подписанные ViewModel.
5. ViewModel вызывает onChange, и экран обновляет сердечки или список.

Почему одно хранилище? Если каждый экран будет вести свой список, они могут разойтись.
Coordinator создаёт один Store и передаёт его всем ViewModel. При этом ViewModel не знают
друг о друге. Store хранит слабые ссылки на наблюдателей, чтобы закрытый экран мог освободиться.

FavouritesViewModel и GalleryViewModel разные, но обе реализуют PhotoGridViewModel.
Это общий договор для экрана сетки: «дай фото, состояние загрузки и обработай действия».
Благодаря этому разметку коллекции и логику ячеек не нужно копировать для второй вкладки.

## Core Data простыми словами

Core Data — система управления объектами и их сохранением. В этом проекте она использует
SQLite как постоянное хранилище. NSPersistentContainer собирает необходимые части Core Data.
Context — рабочая область: мы создаём или удаляем объект и вызываем save, чтобы записать изменения.
Если save не удался, rollback отменяет несохранённые изменения в context.

Схема определена кодом в FavouritesRepository: Favourite хранит уникальный id, дату добавления
и JSON с данными Photo. Само изображение там не хранится — только его адреса. Photo стал Codable:
его можно и прочитать из JSON, и записать обратно. Модель определена кодом вместо редактора
xcdatamodeld; это полноценная Core Data со схемой и SQLite-хранилищем.

Это осознанное упрощение: JSON удобен для восстановления всей фотографии, но для поиска
и сортировки по автору лучше отдельные атрибуты. Сейчас сортируем только по дате добавления.
Изменение схемы в будущем потребует продумать миграцию существующей базы.

Репозиторий выполняет операции через context.perform. У viewContext главная очередь:
await здесь не означает автоматический перенос всей работы в фон. Для большого объёма
избранного следующим улучшением будут фоновый context и порционная выборка.

При ошибке сохранения интерфейс сохраняет прежнее состояние и предлагает повтор.
Пока выполняется запись, повторные нажатия блокируются. Это проверено подменным репозиторием.
Отдельный тест с настоящим SQLite-файлом подтверждает сохранение после нового открытия хранилища.
