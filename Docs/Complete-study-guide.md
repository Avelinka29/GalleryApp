## 2. Как читать этот учебник

Не нужно заучивать документ целиком. Твоя цель — уметь объяснить путь одного действия от пользователя до результата.

Первый проход: разделы 3, 5, 6, 13, 16 и 17. Они дают целую картину.
Второй проход: открывай указанный Swift-файл и находи описанные методы.
Третий проход: отвечай на вопросы в конце вслух, без подсказки, и выполняй упражнения.

Для каждой темы проверь три уровня понимания:

1. **Что происходит?** Например, при нажатии сердечка фото сохраняется в избранное.
2. **Кто за это отвечает?** ViewModel обращается к Store, Store — к Repository.
3. **Почему сделано так?** Один Store исключает независимые расходящиеся списки на разных экранах.

Если умеешь только произнести название паттерна, но не можешь показать его в коде, тему стоит повторить.
Не нужно приписывать себе ручное написание каждой строки: важно честно понимать и объяснять решения,
уметь проверить их и внести небольшое изменение. Если спросят об использовании помощника, отвечай прямо.

## 3. Приложение целиком: основные понятия

**Unsplash** — внешний сервис фотографий. Наше приложение получает от него список описаний фотографий и URL.
Сам список приходит как JSON. Изображения скачиваются отдельно по URL из этого JSON.

**API** — интерфейс, через который программы запрашивают данные у сервиса. Для человека есть сайт,
для приложения — HTTP-запросы к API. GalleryApp не открывает сайт для получения списка и не разбирает HTML.

**Backend** — серверная часть. Собственного backend в проекте нет: клиент напрямую обращается к Unsplash.

**Model** — представление данных. Например, Photo содержит id, описание, URL и автора.

**ViewModel** — состояние экрана и правила его изменения. Например, какие фото уже загружены и можно ли запросить следующую страницу.

**View** — интерфейс. В нашем MVVM сюда относятся UIViewController и его UIView-компоненты.

**Coordinator** — объект, собирающий экраны и управляющий переходами между ними.

**Service / Repository** — объекты для получения и сохранения данных. Сервис работает с API,
репозиторий избранного — с Core Data. Это полезное разделение обязанностей, а не требование к точному названию класса.

**Кеш** — временно сохранённые данные для ускорения повторного использования.
**Постоянное хранилище** — данные, которые приложение сохраняет как пользовательское состояние между запусками.
Кеш картинок и избранное решают разные задачи.

Два основных потока:

```text
Получение фотографий:
ViewController → GalleryViewModel → UnsplashPhotoService → URLSession → Unsplash
      ↑                 ↑                     |
      └── onChange ──────┴──── массив Photo ────┘

Сохранение избранного:
Нажатие → ViewModel → FavouritesStore → FavouritesRepository → Core Data → SQLite
              ↑              |
              └── уведомление после успешного сохранения ──┘
```

Это схемы направления обращений и результатов, а не точный порядок каждого вызова UIKit.

## 5. Архитектура MVVM + Coordinator

### 5.1. Где границы ответственности

В **Model** лежат данные Photo и логика представления необязательного описания.
Доступ к сети и сохранению организован отдельными сервисами.
Во **ViewModel** находятся состояние экрана и команды: загрузить, повторить, выбрать индекс, изменить избранное.
Во **View** создаются UIKit-компоненты и отображается состояние.
В **Coordinator** создаются экраны с зависимостями и выполняются переходы.

ViewController не вычисляет номер следующей страницы и не собирает сетевой URL.
GalleryViewModel не создаёт UIButton и не вызывает pushViewController.
PhotoCell не записывает данные напрямую в Core Data.

### 5.2. Почему наличие UIViewController не превращает проект в MVC

UIViewController — стандартный тип UIKit. UIKit-приложение использует его и при MVVM.
Архитектуру определяет распределение обязанностей: в этом проекте логика состояния вынесена
в ViewModel, а навигация — в Coordinator.

Не говори «у меня MVC, потому что файл называется ViewController». Лучше покажи
GalleryViewModel.load и AppCoordinator.showPhoto: там видно фактическое разделение.

Отличие от MVP полезно понимать, но не надо спорить о единственной правильной терминологии:
здесь View читает состояние ViewModel и обновляется по onChange; отдельного Presenter,
который командует интерфейсом через методы View-протокола, в проекте нет.

### 5.3. Как View узнаёт об изменениях

В ViewModel есть:

```swift
var onChange: (() -> Void)?
```

Это необязательное замыкание без аргументов и результата. Экран назначает обработчик:

```swift
viewModel.onChange = { [weak self] in self?.render() }
```

Когда ViewModel изменила состояние, она вызывает onChange. Экран заново читает свойства и обновляет UI.
Это простая ручная связь между состоянием и отображением. Combine и SwiftUI Observation здесь не используются.
Один onChange подходит для одной View у каждой ViewModel. Для нескольких экранов с общими данными
используется отдельный механизм наблюдателей FavouritesStore.

### 5.4. Dependency Injection — передача зависимостей

```swift
init(service: any PhotoServicing, favourites: FavouritesStore? = nil)
```

ViewModel получает нужные объекты снаружи. Она не создаёт внутри себя конкретный URLSession-сервис.
В приложении Coordinator передаёт реальный сервис, в тесте — подмену.

Это и есть внедрение зависимостей через конструктор. Контейнер DI или сторонняя библиотека для этого не обязательны.
Зависимость по протоколу позволяет менять реализацию без переписывания ViewModel.

### 5.5. Почему две ViewModel используют один экран

GalleryViewModel читает API, FavouritesViewModel читает общий список избранного.
Но обе могут предоставить фото, состояние загрузки и обработчики команд.
PhotoGridViewModel описывает этот общий договор. ViewController работает с `any PhotoGridViewModel`.

Поэтому не нужно копировать UICollectionView, ячейки и обработчики на вторую вкладку.
При этом источник данных и его поведение остаются отдельными.
У избранного loadNextPage только инициирует первое чтение при необходимости: сетевой пагинации у него нет.

### 5.6. Общий Store — не singleton

AppCoordinator создаёт FavouritesStore один раз для своего набора экранов и передаёт его дальше.
В коде нет глобального `FavouritesStore.shared`. «Один экземпляр для этих экранов»
и «глобальный singleton, доступный отовсюду» — разные решения.
В тестах можно создать много независимых Store с разными репозиториями.

## 6. Запуск приложения шаг за шагом

1. Система запускает приложение; точка входа обозначена @main в AppDelegate.
2. AppDelegate возвращает конфигурацию сцены Default Configuration.
3. SceneDelegate получает UIWindowScene и создаёт UIWindow, связанное с этой сценой.
4. SceneDelegate создаёт AppCoordinator и сохраняет его в свойстве, чтобы он продолжал существовать.
5. Coordinator.start создаёт UnsplashPhotoService с ключом из APIConfiguration.
6. Он создаёт GalleryViewModel и FavouritesViewModel с одним FavouritesStore.
7. Для каждой вкладки создаёт ViewController и оборачивает его в UINavigationController.
8. UINavigationController помещаются в UITabBarController.
9. TabBarController назначается rootViewController окна, окно становится видимым.
10. Coordinator запускает чтение избранного. Экран галереи при загрузке своей View запускает запрос фотографий.

Чтение локального избранного и сеть — независимые операции. Галерея не обязана ждать завершения API,
чтобы вкладка избранного могла прочитать сохранённые данные.

Окно — контейнер интерфейса, rootViewController — корневой управляющий экран.
TabBarController выбирает вкладку, NavigationController хранит стек экранов этой вкладки.

```text
UIWindow
└── UITabBarController
    ├── UINavigationController: Галерея
    │   ├── ViewController + GalleryViewModel
    │   └── PhotoDetailsViewController, когда открыто фото
    └── UINavigationController: Избранное
        ├── ViewController + FavouritesViewModel
        └── PhotoDetailsViewController, когда открыто фото
```

Main.storyboard не участвует в запуске: ссылка на него удалена из конфигурации сцены и настроек старта.
LaunchScreen при этом сохранён. Удаление файла storyboard без изменения запуска могло бы сломать приложение;
поэтому настройки были изменены явно, а существующая основа проекта сохранена.

## 7. UIKit для человека со знанием SwiftUI

SwiftUI обычно описывает желаемый интерфейс через View и body. UIKit требует создать объекты,
поместить их в иерархию, задать расположение и обновлять свойства при изменении состояния.

Полезные смысловые соответствия, не точные взаимозаменяемые API:

- SwiftUI Text → UILabel.
- Image → UIImageView; сама UIImage — данные изображения, не View.
- Button → UIButton или UIBarButtonItem для navigation bar.
- VStack / HStack → UIStackView с соответствующей axis.
- ScrollView → UIScrollView.
- TabView → UITabBarController.
- NavigationStack → UINavigationController и его стек контроллеров.
- Сетка → UICollectionView с layout и переиспользованием ячеек.
- Реакция на изменение состояния → в этом проекте onChange и render.

UIViewController управляет своей View, жизненным циклом, дочерними контроллерами и взаимодействиями.
UIView рисует часть интерфейса и участвует в иерархии и обработке событий.

У UIButton действие подключается через addTarget и selector. Например, touchUpInside означает
завершённое нажатие внутри кнопки. Метод помечен @objc, потому что selector работает через Objective-C runtime.
Это обычный способ связывать UIKit-контролы со Swift-методами.

Часть кнопок настраивается через UIAction с замыканием. Делегаты используются для событий коллекции и перелистывания.
Знать нужно все три формы: target-action, callback-замыкание и delegate.

<a id="part-8"></a>
## 8. Жизненный цикл экранов

**init** — создание объекта и получение зависимостей. View ещё не обязательно загружена.

**viewDidLoad** — View загрузилась. Подходит для создания интерфейса, подключения обработчиков
и начального запроса. Не вызывается заново при каждом возврате к уже существующему экрану.
В галерее здесь настраивается коллекция и onChange.

**viewWillAppear** — экран собирается появиться. Может вызываться несколько раз.
PhotoPageViewController проверяет наличие картинки и запускает её загрузку при необходимости.

**viewDidDisappear** — экран исчез. PhotoPageViewController отменяет свою ожидающую задачу изображения.
Это не означает обязательную остановку общей сетевой загрузки ImageLoader: у неё отдельная Task.

**viewDidLayoutSubviews** — UIKit выполнил раскладку. Метод может вызываться много раз;
не следует без причины размещать там повторные сетевые запросы.

**deinit** — объект освобождается из памяти, когда его больше не удерживают сильные ссылки.
Исчезновение экрана и освобождение объекта — разные события. Например, первый экран остаётся
в navigation stack, пока над ним открыт просмотр фото.

`required init?(coder:)` связан с созданием через архивирование / storyboard.
Основной путь наших экранов — программный init с зависимостями. У новых экранов просмотра coder-init возвращает nil.
В исходном ViewController оставлен резервный coder-init, но стартовый storyboard отключён.

<a id="part-9"></a>
## 9. Галерея и UICollectionView

UICollectionView не создаёт сразу отдельную View для каждой фотографии всего списка.
Она переиспользует ячейки по мере прокрутки. Это уменьшает стоимость отображения длинной ленты.

У коллекции есть три ключевые обязанности, вынесенные в разные механизмы:

- **dataSource**: сколько элементов и какую ячейку показать для индекса;
- **delegate**: что делать при выборе и показе элемента;
- **layout**: где находятся элементы и какого они размера.

В нашем проекте dataSource и delegate реализует ViewController, layout создаёт GalleryLayout.
IndexPath содержит section и item. Секция одна, item — позиция фотографии в текущем массиве.
Индекс не является постоянным идентификатором фотографии: при обновлении массива позиция может измениться.

### Регистрация ячейки

PhotoRegistration — сокращённое имя UICollectionView.CellRegistration<PhotoCell, Photo>.
Её замыкание получает ячейку и Photo, связывает кнопки и передаёт изображение в загрузчик.
`dequeueConfiguredReusableCell` получает подходящую ячейку и конфигурирует её.

Регистрация хранится в lazy-свойстве. В configureViews есть `_ = cellRegistration`:
свойство принудительно инициализируется заранее, до первого запроса ячейки из dataSource.
Это появилось после реальной ошибки поздней регистрации и покрыто GalleryRenderingTests.
Не стоит удалять строку как «ничего не делающую», не разобрав её роль.

### Отображение изменений

ViewController хранит renderedPhotos — список, который он уже передал коллекции.
Если новые фото являются добавлением в конец прежнего списка, вставляются только новые index paths.
Если список заменён или из него удалили элемент, вызывается reloadData.

При изменении только сердечек список Photo в галерее не меняется. Экран обновляет кнопки видимых ячеек
без повторной загрузки их картинок. Это уменьшает ненужную работу и мигание.

### Где запускается подгрузка

В willDisplay проверяется, что показывается один из последних шести элементов.
После этого экран просит ViewModel.loadNextPage. Это ранний запрос следующей страницы,
а не реализация UICollectionViewDataSourcePrefetching: такого протокола в проекте нет.

Нажатие на фото вызывает didSelectItemAt и передаёт список с индексом в onSelectPhoto.
Сердечко и подпись автора — отдельные кнопки с отдельными действиями.

<a id="part-10"></a>
## 10. Auto Layout и повороты

Auto Layout описывает отношения между элементами: «левый край равен безопасному левому краю контейнера»,
«ширина картинки равна её высоте». На основе этих ограничений UIKit вычисляет frame.

Основная последовательность программной разметки:

```swift
stack.translatesAutoresizingMaskIntoConstraints = false
view.addSubview(stack)
NSLayoutConstraint.activate([
    stack.leadingAnchor.constraint(equalTo: view.safeAreaLayoutGuide.leadingAnchor),
    stack.trailingAnchor.constraint(equalTo: view.safeAreaLayoutGuide.trailingAnchor)
])
```

Пример намеренно неполный: для реального расположения нужны также вертикальные ограничения.
translatesAutoresizingMaskIntoConstraints отключается, чтобы старый механизм autoresizing mask
не создавал ограничения, конфликтующие с нашими.

Safe area учитывает области, занятые системными элементами и контейнерами.
Она помогает не помещать содержимое под навигацию, вырез экрана и другие перекрывающие элементы.

### Два уровня раскладки

Auto Layout располагает коллекцию на экране и элементы внутри PhotoCell.
Compositional Layout располагает сами ячейки коллекции.
Это разные уровни, они не заменяют друг друга.

GalleryLayout использует ширину контейнера из environment, а не UIScreen.main.bounds.
Из ширины вычитаются боковые отступы по 16, между колонками оставляется 12.
Число колонок рассчитывается с ориентиром на ширину 150, минимум — две.
Картинка квадратная, высота строки дополнительно включает 56 для подписи автора.

Это позволяет перерассчитать сетку при повороте. Проверено две колонки в portrait и четыре в landscape
на использованном iPhone 17. На других ширинах число может отличаться.

### Длинное описание

PhotoPageViewController содержит вертикальный UIScrollView и UIStackView.
Края stack привязаны к contentLayoutGuide, который описывает прокручиваемое содержимое.
Ширина — к frameLayoutGuide, который описывает видимую область. Поэтому содержимое прокручивается
вертикально, но не должно создавать произвольную горизонтальную прокрутку.
Картинка занимает 65% высоты страницы, описание многострочное, автор находится ниже.

Для части текста используются preferredFont и adjustsFontForContentSizeCategory.
Это полезная поддержка масштабирования текста, но не доказательство полного Dynamic Type-аудита:
например, у подписи в ячейке есть ограничение по высоте и двум строкам.

<a id="part-11"></a>
## 11. Модель Photo, JSON и Codable

Photo — struct со свойствами id, description, altDescription, urls и user.
Вложенные ImageURLs, Author и Links представляют вложенные объекты ответа API.

description и altDescription имеют тип String?, потому что сервер может не вернуть описание.
Optional — значение может присутствовать либо отсутствовать; nil не равно пустой строке.

В CodingKeys `altDescription` связано с JSON-ключом `alt_description`.
Это позволяет писать Swift-имя в camelCase, не требуя от API такого же формата.

Codable объединяет Decodable и Encodable:

- JSONDecoder преобразует JSON-байты в Photo;
- JSONEncoder преобразует Photo в JSON-байты для payload избранного.

Photo также Equatable: массивы фотографий можно сравнить в render.
Сравнение учитывает значения свойств, а не только id. Для дедупликации и проверки избранного
используется отдельно именно id.
Sendable выражает возможность безопасной передачи значения между областями конкурентного выполнения;
это не делает любую изменяемую коллекцию автоматически потокобезопасной.

### Как выбирается описание

displayDescription последовательно рассматривает description и altDescription.
Удаляет пробелы и переводы строк с краёв, берёт первую непустую строку.
Если подходящей строки нет — возвращает «Без описания».

Например: description = "   ", altDescription = " Горы " → результат «Горы».
Это лучше, чем проверять только nil: пустое или пробельное описание тоже не полезно пользователю.

### Ссылка автора

attributionURL строится из user.links.html и добавляет utm_source=gallery_app, utm_medium=referral.
Предыдущие одноимённые параметры удаляются, чтобы не дублироваться; остальные сохраняются.
URLComponents помогает безопасно работать с частями URL.
Это отдельная ссылка автора, не URL картинки и не внутренний переход к просмотру.

PhotoPage содержит массив Photo и hasMore. Это результат сервиса с информацией о продолжении ленты,
а не отдельная фотография и не объект Core Data.

<a id="part-12"></a>
## 12. Unsplash, HTTP и сетевой сервис

Открой [PhotoService.swift](../GalleryApp/PhotoService.swift).
Протокол PhotoServicing объявляет fetchPhotos(page:), возвращающий PhotoPage асинхронно и с возможной ошибкой.
UnsplashPhotoService — реальная реализация этого договора.

### Из чего состоит запрос

```text
GET https://api.unsplash.com/photos?page=1&per_page=30
Authorization: Client-ID <локальный Access Key>
Accept-Version: v1
```

GET получает данные. `/photos` — путь endpoint. page и per_page — query-параметры.
Authorization — заголовок с ключом. Настоящее значение ключа в документ не вставляется.
URLSession.data(for:) возвращает Data и URLResponse. Response содержит метаданные ответа,
Data — его тело; тело может быть как корректным JSON, так и сообщением ошибки.

Сервис устанавливает timeoutInterval=30 и reloadIgnoringLocalCacheData для запроса ленты.
Кеширование изображений настраивается отдельно в ImageLoader.
30 секунд — настройка таймаута запроса, не универсальная гарантия времени всей пользовательской операции.

### Почему сначала проверяем HTTP

Успешное завершение URLSession не означает HTTP 200. Например, ответ 401 может прийти без транспортной ошибки.
Поэтому проверяются тип HTTPURLResponse и statusCode, только затем декодируется JSON.

В нашей реализации:

- 200 — декодируем список;
- 401 — unauthorized, ключ отклонён;
- 403 при X-Ratelimit-Remaining=0 или 429 — rateLimited;
- остальные статусы — server с кодом;
- неподходящий ответ или JSON — invalidResponse;
- отсутствие ключа — missingKey ещё до сети.

Ошибка транспорта, например отсутствие интернета, приходит из URLSession. ViewModel переводит
часть таких ошибок в понятное сообщение. Не все ошибки API — отсутствие сети.

### Как определяется конец списка

Если есть заголовок Link, сервис ищет rel="next". Если Link отсутствует,
предполагает продолжение при получении ровно 30 фото. Пустой массив всегда завершает пагинацию.
Разбор Link здесь простой, по содержимому строки; полноценный универсальный HTTP Link parser не реализован.

Квота Unsplash относится к работе сервиса и настройкам приложения в аккаунте.
Не заучивай случайное число запросов: актуальный лимит нужно смотреть в своём кабинете.

<a id="part-13"></a>
## 13. Пагинация, ошибки, обновление и отмена

Пагинация — получение большого списка частями. Она уменьшает первый объём данных и позволяет начать
показ раньше, чем загружена вся лента. Сама по себе она не ограничивает бесконечный рост массива в памяти:
в этой реализации уже полученные страницы остаются в photos до обновления или завершения процесса.

### Состояние GalleryViewModel

- photos — текущий список;
- isLoading — выполняется ли запрос;
- errorMessage — ошибка для отображения;
- hasMore — есть ли смысл запрашивать продолжение;
- nextPage — номер следующего запроса, сначала 1;
- failedRefresh — была ли последняя ошибка при обновлении первой страницы.

private(set) позволяет другим объектам читать свойство, но не произвольно менять его.
Это сохраняет управление состоянием внутри ViewModel.

### Порядок успешной загрузки

1. loadNextPage проверяет hasMore и отсутствие уже показанной ошибки.
2. load проверяет !isLoading.
3. До первого await устанавливает isLoading=true, очищает ошибку и уведомляет View.
4. Выбирает requestedPage: 1 для refresh или nextPage для продолжения.
5. Ожидает сервис.
6. Проверяет отмену задачи, чтобы не применить поздний ненужный ответ.
7. Формирует новый список с удалением дублей по id.
8. Записывает photos, увеличивает nextPage, обновляет hasMore.
9. defer снимает isLoading и уведомляет экран.

### Почему не отправляются параллельные запросы страницы

Событие willDisplay может прийти много раз подряд. Каждый раз создаётся Task,
но решение о запросе принимает ViewModel. Она изолирована MainActor и устанавливает флаг до приостановки.
Следующий вызов видит isLoading=true и выходит. Важны и изоляция состояния, и порядок установки флага.

### Пример ошибки второй страницы

Уже показана страница 1, nextPage=2. Запрос второй страницы падает.
photos остаются прежними, nextPage не увеличивается, появляется ошибка.
События прокрутки не запускают бесконечные повторы, потому что errorMessage не nil.
По нажатию «Повторить» снова запрашивается страница 2.

### Refresh отличается от следующей страницы

Потянуть коллекцию вниз означает обновить список с первой страницы.
Старые фото остаются видны до успешного результата; успех заменяет список.
Ошибка сохраняет прежние фото и помечает failedRefresh. Повтор после такой ошибки снова запрашивает первую страницу.
Refresh, пришедший во время уже идущего запроса, сейчас игнорируется общей защитой isLoading;
отмена старого запроса ради нового refresh не реализована.

### Дубликаты

Set содержит уже известные id. Новый Photo добавляется только если его id ещё не встречался.
Порядок массива сохраняется; сам Set используется только для быстрой проверки принадлежности.
Если API повторно вернул тот же id с изменёнными полями при добавлении страницы,
существующий элемент не обновляется. Refresh заменит список новым ответом.

### Отмена

Task.checkCancellation выбрасывает CancellationError. Также учитывается URLError.cancelled.
Отмена не показывается пользователю как ошибка и не увеличивает номер страницы.
Это поддержка отмены в логике, но не обещание, что каждый уход с экрана автоматически отменяет загрузку ленты:
задача начальной загрузки галереи отдельно не хранится для такой отмены.

### Зачем defer

defer выполняет очистку при выходе из области независимо от успешного результата или обработанной ошибки.
Он предотвращает состояние «спиннер навсегда остался включённым» из-за забытого присваивания в одной ветке.
Он не запускает отдельный поток и не означает «выполнить через некоторое время».

<a id="part-14"></a>
## 14. Изображения, кеш и переиспользование ячеек

### 14.1. Список фотографий и сами картинки загружаются отдельно

Сервис возвращает Photo с URL. Только потом ячейка вызывает ImageLoader.image(for:).
Поэтому галерея может уже иметь названия и авторов, а отдельная картинка ещё загружаться или завершиться ошибкой.
Ошибка одного изображения не должна превращать всю страницу в ошибку списка.

Для сетки используется urls.small и загрузчик с размером подготовки до 600 × 600.
Для просмотра — urls.regular и отдельный загрузчик до 1600 × 1600.
Оба загрузчика создаёт Coordinator: один разделяют сетки, второй — страницы просмотра.

### 14.2. Что делает ImageLoader

Порядок действий:

1. Проверяет NSCache: если готовая UIImage есть, возвращает её.
2. Проверяет словарь requests: если такой URL уже загружается, ожидает существующую Task.
3. Создаёт новую Task, выполняет URLSession.data(from:).
4. Проверяет успешный HTTP-статус, создаёт UIImage, асинхронно подготавливает уменьшенное изображение.
5. Сохраняет результат в NSCache и возвращает его.
6. Через defer удаляет завершённую Task из requests, в том числе при ошибке.

Если не удалять ошибочную Task из словаря, «Повторить» мог бы получать ту же завершённую ошибку
вместо новой попытки. Если не объединять запросы, две ячейки одного URL могли бы скачать одно изображение дважды.

### 14.3. Два уровня кеша

**NSCache<NSURL, UIImage>** хранит уже подготовленные картинки в памяти.
Стоимость картинки приблизительно считается как bytesPerRow × height у CGImage.
totalCostLimit установлен в 48 × 1024 × 1024 байт на загрузчик. Это рекомендация кешу,
не жёсткий предел всей памяти процесса. Две отдельные NSCache имеют два отдельных лимита.

**URLCache** хранит HTTP-ответы. Настроены 16 × 1024 × 1024 байт памяти и 100 × 1024 × 1024 диска
для конфигурации загрузчика, политика useProtocolCachePolicy. Использование сохранённого ответа
зависит от HTTP-заголовков и политики кеширования; нельзя обещать, что любая картинка всегда доступна офлайн.

UIImage в NSCache и HTTP-данные в URLCache — разные представления и разные уровни работы.

### 14.4. Опасность переиспользования на простом примере

1. Ячейка показывает фото A и запускает его медленную загрузку.
2. Пользователь прокрутил список.
3. UIKit отдаёт эту же ячейку для фото B.
4. Загрузка A завершается позже загрузки B.
5. Если без проверки установить результат, в ячейке B внезапно появится A.

В PhotoCell перед новой загрузкой отменяется прежняя imageTask.
prepareForReuse очищает фото, зависимости, замыкания, изображение, подписи и состояние загрузки.
После await проверяются `!Task.isCancelled` и соответствие текущего photo.id ожидаемому id.
Только после этих проверок результат попадает в imageView.

Нужна не только отмена: отмена кооперативна, запоздавший ответ всё ещё может существовать.
Проверка id дополнительно связывает ответ с теми данными, для которых ячейка сейчас настроена.

### 14.5. Отмена потребителя и общей загрузки

Task у ячейки ожидает результат ImageLoader. Task внутри ImageLoader может обслуживать несколько потребителей.
Отмена задачи ячейки не вызывает отмену общей загрузки. Она может закончиться и прогреть кеш для других экранов.
Это осознанный компромисс: исключаем мешающие отмены, но можем скачать картинку, которая уже не нужна ни одной видимой ячейке.
Учёт числа потребителей и отмена общей загрузки при нуле — возможное дальнейшее улучшение, сейчас его нет.

### 14.6. scaleAspectFill и scaleAspectFit

В сетке scaleAspectFill заполняет квадрат, сохраняя пропорции; края картинки могут обрезаться.
clipsToBounds не даёт изображению рисоваться за пределами UIImageView.
В просмотре scaleAspectFit помещает картинку целиком в отведённую область с сохранением пропорций;
свободные полосы вокруг картинки допустимы.

### 14.7. Что говорить о плавности

«Используются переиспользование ячеек, изображения подходящего размера, кеш,
объединение запросов и добавление новых элементов вместо перезагрузки всего списка при пагинации».
Это конкретные меры, а не доказательство 60 или 120 FPS.

byPreparingThumbnail — асинхронная подготовка изображения. Здесь исходная UIImage сначала создаётся из Data;
нельзя утверждать, что проект реализует специальный ImageIO-downsampling, который никогда не держит
исходное представление в памяти. Instruments и более строгая оптимизация декодирования — следующий уровень работы.

<a id="part-15"></a>
## 15. Просмотр фотографии и свайпы

### Как открывается фото

ViewController получает didSelectItemAt, снимает выделение ячейки и проверяет индекс.
Затем вызывает onSelectPhoto с массивом фотографий и индексом.
Coordinator создаёт PhotoDetailsViewModel, PhotoDetailsViewController и делает push в NavigationController выбранной вкладки.

На сайте открывается только явная ссылка автора. Нажатие на само фото ведёт во внутренний просмотр.
Раньше, до этапа 4, нажатия на фото были отключены, а ссылка автора уже работала — отсюда возникало ощущение,
что приложение всегда отправляет пользователя на Unsplash.

### Почему две разновидности ViewController для просмотра

PhotoDetailsViewController — контейнер перелистывания и navigation bar.
PhotoPageViewController — содержимое одной страницы: изображение, текст, ссылка, спиннер и повтор картинки.
Так управление списком страниц не смешано с отображением одной фотографии.

### UIPageViewController

Создан с transitionStyle .scroll и горизонтальной ориентацией.
DataSource возвращает страницу с предыдущим или следующим индексом.
Если индекс вне массива, makePage возвращает nil — перелистывание за границу невозможно.

Начальная страница назначается через setViewControllers. Pager добавляется как дочерний контроллер:
addChild → добавление его View → constraints → didMove(toParent:).
Просто добавить pager.view без корректного containment недостаточно для правильного управления жизненным циклом.

Когда жест завершён, delegate получает transitionCompleted.
Только при completed=true выбирается индекс фактически отображаемой страницы.
Пользователь может потянуть страницу и отменить жест; в этом случае выбранная фотография не должна измениться.

### Зачем снимок списка

PhotoDetailsViewModel получает массив уже загруженных фото при открытии.
Он не запрашивает следующие страницы API и не перестраивает список при каждом изменении избранного.
Это обеспечивает устойчивые индексы во время свайпа.

Если удалить фото из избранного в просмотре, сердечко станет пустым, но текущая страница не исчезнет.
После возврата в список избранного удалённого фото не будет. Свайпы по открытому снимку остаются предсказуемыми.
Это допущение задания, которое стоит озвучить, а не выдавать за автоматическую пагинацию внутри просмотра.

init? ViewModel возвращает nil для пустого массива или неправильного стартового индекса.
За счёт этого создаётся только корректное начальное состояние. Методы выбора также проверяют границы.

<a id="part-16"></a>
## 16. Избранное и синхронизация экранов

### 16.1. Почему нельзя держать три независимых списка

Если галерея, просмотр и избранное изменяют собственные массивы, один экран может показывать заполненное сердце,
а другой — пустое. Нужно одно место, которое определяет актуальный пользовательский выбор.
В нашем приложении это FavouritesStore.

Он хранит photos, isLoading, isSaving, isLoaded, errorMessage и failedPhoto для повтора.
Общее состояние живёт в памяти, а Repository обеспечивает сохранение на диск.
Store и Repository не дублируют друг друга: первый организует состояние для интерфейса, второй знает детали хранения.

### 16.2. Полная цепочка нажатия

1. UIButton вызывает обработчик ячейки или экрана просмотра.
2. Обработчик передаёт команду ViewModel.
3. ViewModel вызывает Store.toggle(photo).
4. Store проверяет, что первоначальное чтение завершено и другой операции сейчас нет.
5. По id определяет желаемое состояние: добавить или удалить.
6. Устанавливает isSaving=true и уведомляет наблюдателей: сердечки временно отключаются.
7. Repository выполняет запись.
8. После успеха Store удаляет прежний элемент с тем же id и при добавлении вставляет фото в начало массива.
9. defer снимает isSaving и вызывает уведомления.
10. ViewModel вызывают onChange; галерея обновляет сердечки, избранное — свой список, просмотр — кнопку в navigation bar.

Новое избранное оказывается первым; при чтении базы используется сортировка по addedAt по убыванию.
Для уже существующей записи Repository сохраняет исходную дату, если просто обновляет её payload.

### 16.3. Почему состояние меняется после save

Мы не показываем добавление успешным до подтверждённого сохранения.
При ошибке записи старый массив остаётся прежним, выводится сообщение.
Это подход «сначала подтверждение, потом отображение результата».
Оптимистичное обновление с последующим откатом возможно, но здесь не реализовано.

### 16.4. Наблюдатели

FavouritesObserver — протокол с favouritesDidChange.
GalleryViewModel, FavouritesViewModel и PhotoDetailsViewModel регистрируются у Store.
Store хранит WeakObserver, внутри которого weak-ссылка на наблюдателя.
Когда закрытая ViewModel освобождается, weak становится nil; мёртвые ссылки удаляются при обслуживании списка.

Это собственный небольшой механизм уведомления без Combine и NotificationCenter.
Один Store уведомляет несколько ViewModel; каждая ViewModel использует свой onChange для своего экрана.

### 16.5. Ошибка и повтор

При ошибке чтения isLoaded остаётся false, если успешного чтения ещё не было.
Сердечки нельзя менять до первоначальной загрузки: иначе приложение могло бы принять неполное знание о базе за пустой список.

При ошибке записи запоминается failedPhoto. retry повторяет изменение этой фотографии.
Это важно, если пользователь уже успел перелистнуть на другую: повтор должен относиться к неудавшейся операции.
Если неудачной записи нет, retry повторяет чтение.
Новая операция или новое чтение очищают прежнюю ожидающую ошибку согласно текущей реализации.

Пока идёт запись, повторные нажатия не ставятся в очередь и не создают вторую запись: они блокируются / игнорируются.
Это ограничение ради простой последовательной модели, а не параллельная запись каждого сердечка.

### 16.6. Избранное не является лайками Unsplash

Локальное добавление не отправляет запрос изменения аккаунта Unsplash и не требует пользовательского OAuth-входа.
Нельзя говорить, что приложение синхронизирует лайки между телефоном и сайтом.
Без отдельной серверной синхронизации избранное также не появляется автоматически на другом устройстве.

<a id="part-17"></a>
## 17. Core Data подробно

### 17.1. Что такое Core Data

Core Data — framework для управления графом объектов и сохранением данных.
SQLite — один из способов постоянного хранения, который использует наш контейнер.
Поэтому точный ответ: «Я использую Core Data с SQLite-хранилищем», а не «Core Data — это просто SQL-база».
SQL-запросы вручную приложение не составляет.

### 17.2. Основные объекты

**NSManagedObjectModel** описывает схему: какие сущности и атрибуты существуют.
**NSEntityDescription** описывает одну сущность.
**NSAttributeDescription** описывает конкретный атрибут и его тип.
**NSPersistentContainer** собирает model, persistent store coordinator и контексты.
**NSManagedObjectContext** — рабочая область, где выполняются выборка и изменения объектов.
**NSManagedObject** — объект, управляемый Core Data.
**NSFetchRequest** — описание выборки, в том числе условий и сортировки.

В проекте нет отдельного сгенерированного класса Favourite: используется NSManagedObject
и доступ к атрибутам по именам через value/setValue. Это компактно, но менее типобезопасно,
чем специализированный класс с типизированными свойствами.

### 17.3. Где схема, если нет xcdatamodeld

Схема создана программно в FavouritesRepository.makeModel.
Сущность Favourite содержит:

- id: String — идентификатор фотографии;
- payload: binary Data — JSON-представление Photo;
- addedAt: Date — время добавления.

Атрибуты обязательны. Для id задано ограничение уникальности.
Отсутствие визуального файла модели не означает отсутствие Core Data.
Контейнер получает NSManagedObjectModel напрямую при инициализации.

### 17.4. Почему JSON внутри Core Data

Нужно восстановить Photo: автора, описание и URL, даже когда фотография отсутствует в текущей ленте API.
Codable позволяет сохранить все эти метаданные в payload.
При этом id и addedAt вынесены отдельно для выборки и сортировки.

Это допущение небольшой реализации. База не может удобно выполнять обычную предикатную выборку
по имени автора, спрятанному внутри JSON payload. Для поиска по полям и более сложных связей
стоило бы сделать отдельные атрибуты и, при необходимости, сущности.

Сами пиксели изображения в payload не записываются. URL — адрес, а не содержимое картинки.

### 17.5. Загрузка persistent store

prepare создаёт и сохраняет Task загрузки хранилища. Параллельные обращения ожидают одну загрузку.
loadPersistentStores имеет completion handler. withCheckedThrowingContinuation связывает
этот callback с async/await: при успехе continuation возобновляется без ошибки, при сбое — с ошибкой.

Continuation должна быть возобновлена ровно один раз для одной ожидающей операции.
Забытое resume приводит к зависанию ожидающей задачи, повторное — к ошибке использования continuation.
В этой конфигурации контейнер имеет одно описание persistent store.

Если загрузка не удалась, loading сбрасывается, чтобы можно было повторить попытку.
При успехе завершённая Task остаётся и последующие prepare не открывают базу повторно.

### 17.6. Чтение избранного

Repository создаёт NSFetchRequest для Favourite, задаёт сортировку addedAt по убыванию,
получает объекты через context.fetch и декодирует payload каждого в Photo.
Если payload отсутствует или повреждён, операция сообщает ошибку; незаметное пропускание повреждённых записей не реализовано.

### 17.7. Добавление и отсутствие дубликатов

Сначала выполняется выборка с predicate `id == %@`. `%@` подставляет значение параметра;
это не ручное склеивание SQL со строкой пользователя.
Если объект найден, он обновляется; если нет, создаётся новый.
Присваиваются id и payload, дата задаётся при первом добавлении, затем вызывается save.

Есть несколько уровней защиты: последовательные изменения Store, поиск записи перед вставкой,
ограничение уникальности id в модели. Это не полноценное разрешение конфликтов нескольких устройств или множества writers;
в текущем приложении один общий Store управляет записью.

### 17.8. Удаление и rollback

При enabled=false найденные объекты помечаются на удаление через context.delete.
Для постоянного сохранения результата всё равно требуется context.save.
При ошибке вызывается rollback: несохранённые изменения в контексте откатываются, ошибка передаётся дальше.
Store не меняет своё отображаемое состояние до успеха Repository.

### 17.9. Очередь контекста

Используется container.viewContext — контекст главной очереди. Все его операции выполняются через context.perform.
perform обеспечивает выполнение на очереди контекста; в этом случае эта очередь не становится фоновой только из-за await.
shouldAddStoreAsynchronously относится к подключению persistent store, а не автоматически ко всем последующим выборкам.

Для небольшого избранного решение простое. Для большого объёма данных лучше рассмотреть фоновые контексты,
порционные выборки и измерение задержек. Сейчас весь список метаданных читается сразу.

### 17.10. Что происходит при перезапуске и удалении приложения

При обычном завершении процесса память теряется, но SQLite-файл в контейнере приложения сохраняется.
При следующем запуске новый Store читает базу и восстанавливает photos.
Обычное удаление приложения удаляет его локальные данные; переустановка не является проверкой сохранения между запусками.
Удаление приложения и повторный запуск установленного приложения — разные действия.

### 17.11. Миграции

Если менять схему выпущенной базы, нужно продумать версионирование модели и миграцию.
В проекте не разработан отдельный сценарий эволюции нескольких версий схемы.
Нельзя обещать, что произвольная замена типа или удаление атрибута пройдут без потери данных.

<a id="part-18"></a>
## 18. Swift Concurrency без распространённых заблуждений

**async** — функция может приостанавливаться и возобновляться.
**await** — точка ожидания асинхронного результата.
**throws / try** — функция может выбросить ошибку; вызывающий код должен её обработать или передать дальше.
**Task** — единица асинхронной работы, которую можно запустить из синхронного обработчика UIKit.

Пример из смысла проекта:

```swift
Task {
    await viewModel.loadNextPage()
}
```

Обработчик не ждёт завершения сетевого запроса синхронной блокировкой главного потока.
Но Task, созданная внутри MainActor-контекста, не является обещанием «выполнить весь код в фоне».

### MainActor

MainActor изолирует состояние, связанное с UI, и обеспечивает выполнение actor-isolated кода на главном исполнителе.
Во время await задача может приостановиться, и другой код на MainActor получит возможность выполняться.
Поэтому «мой класс @MainActor» не отменяет необходимости isLoading: между приостановками
несколько операций могут логически пересекаться.

Сеть выполняется механизмами URLSession; ожидание её результата не означает занятый бесконечным ожиданием главный поток.
Однако синхронная тяжёлая обработка данных до или после await может занимать главный поток.
JSON-декодирование небольших страниц здесь не вынесено в специальный фоновый обработчик.

### Кооперативная отмена

task.cancel помечает задачу отменённой. Код и вызываемые операции должны учитывать отмену.
Task.isCancelled проверяет флаг, Task.checkCancellation выбрасывает CancellationError.
Нельзя рассчитывать, что cancel мгновенно уничтожит любой выполняющийся код.

### async let в тесте кеша

Тест запускает два ожидания одного URL через async let и затем ожидает оба.
Ожидается один сетевой запрос и один объект результата из общего загрузчика.
Это проверка конкурирующих обращений, а не просто два последовательных чтения кеша.

### CheckedContinuation в тестах

Подменный сервис может остановить ответ на continuation. Тест дожидается начала запроса,
вызывает второй запрос и убеждается, что он не прошёл, затем вручную завершает первый.
Так конкурентное поведение проверяется управляемо, без случайного sleep на несколько секунд.

<a id="part-19"></a>
## 19. ARC, weak и время жизни объектов

ARC управляет освобождением объектов классов по сильным ссылкам.
Если два объекта удерживают друг друга сильно и извне они уже не нужны, может возникнуть retain cycle.

Типичный риск в нашем проекте:

```text
ViewController → ViewModel → onChange-замыкание → ViewController
```

ViewController хранит ViewModel, ViewModel хранит onChange. Если замыкание сильно захватит self,
цикл может удерживать закрытый экран. `[weak self]` разрывает сильную обратную ссылку.
После освобождения объекта weak становится nil, поэтому self внутри такого замыкания optional.

Сильное удержание Coordinator в SceneDelegate, напротив, необходимо: он должен жить вместе со сценой.
Не нужно делать все ссылки weak. Weak — способ выразить отсутствие владения, а не универсальная оптимизация памяти.

В Coordinator замыкание onSelectPhoto захватывает self и navigation слабо,
чтобы цепочка экран → замыкание → NavigationController → экран не создала цикл.
Store хранит наблюдателей слабо, поскольку ViewModel уже хранит Store.

Если внутри Task выполнен `guard let self`, локальная сильная ссылка может удерживать объект
до конца этой области, включая последующие await. Само наличие `[weak self]` в заголовке
не означает отсутствия любого временного удержания после разворачивания.

Array и Photo — значения; классы ViewModel, Store и контроллеры — ссылочные объекты.
Для массивов Swift применяет copy-on-write: передача массива по значению не обязана немедленно копировать весь буфер,
но семантика всё равно остаётся значимой для независимого снимка списка.

На защите достаточно объяснить конкретный цикл и показать, где стоит weak.
Полное отсутствие утечек можно утверждать только после соответствующих проверок, а не по одному поиску weak в коде.

<a id="part-20"></a>
## 20. Swift-конструкции, которые нужно понимать

### let, var, private и private(set)

let фиксирует привязку свойства / переменной; var допускает изменение.
У свойства let, содержащего ссылку на класс, сам объект всё ещё может менять своё внутреннее состояние.
private ограничивает доступ, private(set) оставляет чтение снаружи, но запрещает внешнее присваивание.

### struct, class, final и enum

Photo — struct: удобное значение данных. ViewModel и Store — class: общее изменяемое состояние и идентичность.
final запрещает наследование от класса. Это выражает намерение дизайна, а не само по себе архитектурный паттерн.
PhotoServiceError — enum с конечным набором ошибок; server(Int) дополнительно несёт код ответа.

### protocol, any, extension

Протокол задаёт требования. `any PhotoServicing` хранит реализацию, конкретный тип которой вызывающему коду не нужен.
Это отличается от наследования одного класса от другого.
extension добавляет реализацию методов / свойств. Например, PhotoGridViewModel получает общие действия избранного.

### Optional, guard let, if let, ?? и ?.

Optional выражает отсутствие значения. guard let разворачивает значение или досрочно выходит.
if let выполняет ветку при наличии значения. `??` даёт запасное значение, optional chaining `?.`
выполняет обращение только при наличии объекта.
Не заменяй проверки на `!` ради краткости: неверное предположение о наличии значения приведёт к падению.

### Замыкания и @escaping

Замыкание — блок кода, который можно передать и сохранить как значение.
@escaping у параметра означает, что замыкание может использоваться после возврата функции,
например, сохраниться в PhotoCell до будущего нажатия.
`(() -> Void)?` — необязательное действие без входных аргументов и результата.
`(([Photo], Int) -> Void)?` — действие со списком и индексом.

### lazy

lazy-свойство инициализируется при первом обращении. Оно удобно, когда настройка использует self.
Для cellRegistration мы намеренно вызываем первое обращение раньше запроса первой ячейки.

### map, compactMap, Set

map преобразует каждый элемент: Photo → id.
compactMap также отбрасывает nil: удобно при переборе двух optional-описаний.
Set хранит уникальные значения и используется для проверки id при дедупликации.
Set не заменяет упорядоченный массив, когда нужно сохранить порядок показа фотографий.

### do/catch, try?, LocalizedError

do/catch позволяет различить ошибки. try? превращает ошибку в nil и подходит там,
где детали ошибки намеренно сводятся к одному результату. Например, конфигурация возвращает nil,
если локальный plist невозможно прочитать.
LocalizedError позволяет дать собственное описание, пригодное для сообщения пользователю.

### @discardableResult

Метод возвращает полезный результат, но вызывающему разрешено его не использовать без предупреждения компилятора.
Store.toggle возвращает Bool: экран просмотра использует его для обработки ошибки,
а другой вызывающий код может ориентироваться на опубликованное состояние Store.

### Импорты

Foundation — базовые типы, URLSession, JSON и работа с данными.
UIKit — интерфейс, контроллеры и UIImage.
CoreData — слой постоянного хранения.
Testing — unit-тесты Swift Testing.
XCTest и XCUIAutomation — UI-тест запуска приложения и взаимодействия с вкладками.

<a id="part-21"></a>
## 21. Состояния интерфейса и повтор

Нужно различать три независимых вида загрузки: список API, отдельную картинку и локальное избранное.
Успех одного вида не означает успех остальных.

### Пустая галерея и загрузка

Если фотографий нет и isLoading=true, экран показывает UIContentUnavailableConfiguration.loading.
Если списка нет и есть ошибка, показывает сообщение с повтором.
Если списка нет и ошибки нет, показывает пустое состояние.

### Ошибка следующей страницы

Если фото уже есть, они остаются на экране. Спиннер или ошибка показываются в нижнем блоке,
а не заменяют весь список. Это важно: ошибка сети не должна уничтожать уже загруженный результат.

### Ошибка картинки

У отдельной ячейки или страницы есть свой спиннер и кнопка повтора.
При неудаче загрузки изображения повторяется ImageLoader-запрос, а не обязательно весь List Photos.

### Ошибка избранного

В сетке отображается сообщение через состояние ViewModel; при ошибке изменения из просмотра показывается alert.
Повтор связан с сохранённой неудачной операцией Store. До первого успешного чтения базы сердечки отключены.

В пустом избранном сейчас также видна кнопка «Повторить», которая перечитывает локальное хранилище.
Её можно сделать более уместной по тексту / показывать только при ошибке как небольшое улучшение UX.
Не путай её наличие с фактической ошибкой базы.

<a id="part-22"></a>
## 22. Ключ, настройки и запуск на устройстве

### Три разных файла

**Info.plist** — настройки приложения и сцены.
**Secrets.plist** — локальная конфигурация с Access Key, попадающая в bundle при сборке.
**Favourites.sqlite** — пользовательские данные избранного, создаваемые Core Data во время работы.

Secrets.plist не является базой данных. Access Key — строка для доступа к API, а не изображение,
не логин пользователя и не содержимое избранного. Для чтения List Photos в этой реализации Secret Key не нужен.

APIConfiguration.accessKey находит Secrets.plist в Bundle.main, читает Data и декодирует Property List.
Пробелы вокруг значения удаляются. Пустая строка или YOUR_ACCESS_KEY считаются отсутствующим ключом.
После изменения файла нужно пересобрать приложение, чтобы новая копия попала в bundle.

### Git и реальная защита

.gitignore исключает Secrets.plist из добавления в Git. Но .gitignore не удаляет секрет из уже созданной истории.
Если ключ когда-либо утёк, нужно отозвать / заменить его и отдельно разбираться с историей.
В проведённой проверке настроенный ключ не найден в истории проекта.

Локальный plist защищает репозиторий от случайного коммита ключа, но не делает ключ неизвлекаемым из приложения.
Шифрование строк внутри приложения также не даёт абсолютной защиты, если клиент умеет сам их расшифровать.
Для публичного продукта нужна отдельная продуманная серверная схема и ограничения доступа;
в проекте такого backend нет. Не говори, что ключ защищён Keychain: Keychain здесь не используется.

### Запуск в Xcode

1. Открыть GalleryApp.xcodeproj и выбрать схему GalleryApp.
2. В новом клоне создать локальный plist по [Unsplash-setup.md](Unsplash-setup.md).
3. Выбрать установленный iOS Simulator либо своё устройство.
4. Нажать ⌘R для сборки и запуска; ⌘U для тестов.
5. Для физического устройства настроить Team / signing и убедиться, что Xcode поддерживает его ОС.

Deployment target 17.0 означает минимальную ОС приложения. SDK — набор интерфейсов, с которым приложение собирается.
Версия runtime симулятора — среда фактического запуска. Это три разные настройки.
Уменьшение deployment target не заставит старую версию Xcode поддерживать более новую ОС подключённого телефона.

Долгая загрузка Xcode может быть сборкой, запуском симулятора, установкой или работой сети уже запущенного приложения.
Сначала определи этап по статусу Xcode и интерфейсу, а не меняй все настройки сразу.

<a id="part-23"></a>
## 23. Тесты: что проверяют все 23 теста

Тест — исполняемый сценарий с проверками ожидаемого результата. Зелёный запуск означает,
что конкретные проверенные сценарии прошли; это не математическое доказательство отсутствия всех ошибок.

### Swift Testing

Unit-тесты используют @Test, #expect и #require.
#expect фиксирует проверку условия. #require нужен, когда дальнейшие шаги невозможны без значения,
например, необходимо получить созданную ячейку или URL.
@testable import даёт тестам доступ к internal-объявлениям модуля, не делая их публичным API приложения.

### Подмены

StubPhotoService возвращает запланированные результаты и запоминает номера страниц.
SuspendedPhotoService удерживает ответ, чтобы проверить перекрывающиеся вызовы.
FavouritesStub имитирует успех или ошибку чтения/записи.
StubURLProtocol перехватывает запросы URLSession в тестовой сессии и возвращает заданный HTTP-ответ.

Эти тесты не расходуют квоту API: они не обращаются к реальному Unsplash.
UI-тест запускает настоящее приложение; если там есть ключ, само приложение может запросить первую страницу.
Проверки UI-теста от содержимого этого ответа не зависят.

### Точный состав

**GalleryPaginationTests — 6 тестов:**

1. failedPageRetry: неудачная страница сохраняет список, повторяет нужный номер, дубликаты не добавляются.
2. overlappingRequests: пока запрос не закончен, повторный вызов и refresh не создают новый запрос.
3. refreshRetry: ошибка обновления сохраняет старые фото, повтор начинает с первой страницы.
4. emptyPage: пустая лента останавливает пагинацию, ручной повтор загружает первую страницу.
5. missingDescription: отсутствие описания корректно декодируется, используется запасной текст; проверяются параметры attribution URL.
6. cancelledResponse: поздний ответ отменённой задачи не применяется; новый вызов запрашивает тот же номер страницы.

**PhotoServiceTests — 7 тестов:**

7. listPhotosRequest: путь, page, per_page, Authorization; ключ не помещается в URL; обработка Link и описания.
8. rateLimit: специальная ошибка при исчерпании лимита.
9. missingKey: отсутствие ключа останавливает работу до сети.
10. imageCache: два конкурирующих запроса одного URL и повторное чтение используют одну загрузку / кеш.
11. invalidJSON: неверный JSON не превращается в успешный пустой список.
12. unauthorized: HTTP 401 превращается в ошибку ключа.
13. emptyResponseWithNextLink: пустой ответ завершает ленту даже при rel=next.

**GalleryRenderingTests — 1 тест:**

14. firstLoadedCell: создаётся первая реальная ячейка без ошибки регистрации; выбор передаёт фото
    обработчику просмотра и не вызывает обработчик внешней ссылки.

**PhotoDetailsTests — 2 теста:**

15. selectionAndBoundaries: выбранный индекс, номер в заголовке и границы списка.
16. invalidInitialSelection: пустой список и неверный начальный индекс не создают ViewModel просмотра.

**FavouritesTests — 4 теста:**

17. sharedState: добавление и удаление согласованы между ViewModel галереи, избранного и просмотра.
18. saveFailure: ошибка записи оставляет состояние прежним, повтор выполняет нужное изменение.
19. loadFailure: ошибка чтения не маскируется под успешный пустой список; редактирование недоступно до успешного чтения.
20. concurrentWrites: повторные нажатия во время незавершённой записи не создают ещё одну запись.

**FavouritesPersistenceTests — 1 тест:**

21. persistence: настоящая временная SQLite-база; сохранение при новом экземпляре Repository,
    отсутствие дублей при повторном добавлении, сохранение удаления.
    Это проверка повторного открытия хранилища, не буквальное завершение процесса приложения внутри unit-теста.
    Перезапуск процесса отдельно проверялся в симуляторе.

**GalleryAppTests — 1 тест:**

22. descriptionFallback: приоритет description, очистка пробелов, переход к altDescription и окончательный запасной текст.

**GalleryAppUITests — 1 тест:**

23. testTabsOpenWithoutDependingOnNetworkContent: запуск, наличие вкладок, переход в избранное и обратно.

### Как объяснить один тест подробно

Лучший пример — failedPageRetry:

```text
Arrange: подмена выдаст страницу 1, ошибку, затем результат страницы 2.
Act: загрузить первую, попробовать вторую, нажать повтор.
Assert: после ошибки первая осталась; запросы [1, 2, 2]; дубликат не добавился.
```

Arrange / Act / Assert — подготовка / действие / проверка. Это удобная форма объяснения,
даже если код не разделён комментариями с такими названиями.

PhotoServiceTests помечены serialized, потому что подмена URLProtocol использует общее статическое тестовое состояние.
NSLock защищает доступ к этому состоянию со стороны вызовов URLProtocol.
`@unchecked Sendable` у тестовой подмены означает ответственность разработчика за корректную синхронизацию,
а не автоматическую безопасность, проверенную компилятором.

### Чего тесты не доказывают

Нет заявления о 100% покрытии кода, идеальном VoiceOver, работе на всех iPad,
измеренной плавности, полном офлайн-режиме или отсутствии любых утечек памяти.
Тест ячейки вызывает delegate программно; настоящий touch проверялся отдельно в симуляторе.

## 24. Git, PR и SwiftLint

### Git

Git хранит историю файлов. Коммит — зафиксированное логическое изменение.
Ветка — отдельная линия работы. Remote origin — адрес удалённого репозитория.
main — основная ветка, feature-ветки использовались для каждого этапа.

PR — предложение перенести изменения ветки в main с описанием и проверкой diff.
Создание PR не объединяет код. Merge — отдельное действие; его выполняла пользовательница после просмотра.
После merge следующая ветка создавалась от обновлённого main, чтобы не потерять принятые изменения.

Полезные команды для чтения состояния:

```sh
git status --short --branch
git diff
git diff --cached
git log --oneline -10
git remote -v
git check-ignore GalleryApp/Secrets.plist
git ls-files GalleryApp/Secrets.plist
```

git diff показывает незастейдженные изменения, --cached — подготовленные к коммиту.
Последняя команда для Secrets.plist должна не выводить ничего.
Не запускай reset --hard или force push, пытаясь «просто почистить проект»: они могут уничтожить работу или переписать историю.
В этом проекте весь .xcodeproj не исключён из Git — без файла проекта другому человеку было бы сложнее воспроизвести сборку.

### SwiftLint

Линтер проверяет правила стиля и ряд потенциально проблемных конструкций.
Он не заменяет компилятор, тесты и ручную проверку поведения.
Запускается из корня репозитория:

```sh
sh Scripts/lint.sh
```

Используется SwiftLint 0.65.1; установка и выбор DEVELOPER_DIR описаны в README.
Файл .swiftlint-baseline.json сохраняет пять исходных замечаний AppDelegate.
Поэтому корректная формулировка — «нет новых нарушений относительно baseline»,
а не «в проекте вообще никогда нет ни одного замечания».
Не нужно добавлять собственные новые нарушения в baseline ради зелёной проверки.

<a id="part-25"></a>
## 25. Вопросы на защите с ответами

Это вероятные вопросы, а не гарантированный список интервьюера. Короткий ответ — отправная точка:
после него нужно уметь открыть соответствующий файл и показать пример. Не заучивай ответы без понимания.

### О приложении и архитектуре

**1. Что делает приложение?**

«Показывает фотографии Unsplash, позволяет открывать их с описанием, листать загруженный список
и сохранять избранное локально. Избранное остаётся после перезапуска».

**2. Почему выбран UIKit?**

«Это требование задания. Я знакома со SwiftUI, а здесь использовала UIKit: коллекцию, контроллеры,
делегаты и Auto Layout. SwiftUI-компонентов в готовой реализации нет».

**3. Какая архитектура и где она видна?**

«MVVM + Coordinator. GalleryViewModel управляет страницами и состоянием,
ViewController отображает коллекцию, AppCoordinator создаёт экраны и открывает просмотр».

**4. Почему это не MVC, если есть ViewController?**

«UIViewController — тип UIKit, а не автоматическое определение архитектуры.
В моём проекте он относится к View-слою. Сетевое состояние вынесено во ViewModel,
переходы — в Coordinator». Покажи GalleryViewModel.load и AppCoordinator.showPhoto.

**5. Что будет, если убрать Coordinator?**

«Создание следующего экрана и его зависимостей придётся перенести в другое место,
например в контроллер галереи. Тогда он будет знать больше о других экранах.
Coordinator отделяет отображение от сборки и навигации».

**6. Почему ViewModel не знает о UIKit?**

«Её задача — состояние и правила работы с данными. Отсутствие UIKit-зависимостей
упрощает проверку этой логики без реального интерфейса». Обрати внимание:
ImageLoader использует UIImage, но это отдельная зависимость View-слоя, не GalleryViewModel.

**7. Как экран обновляется после загрузки?**

«ViewModel сохраняет результат и вызывает onChange. ViewController подписан замыканием,
вызывает render и читает новые значения». В отличие от SwiftUI, здесь нет пересчёта body.

**8. Зачем передавать сервис через протокол?**

«ViewModel нужен договор fetchPhotos, а не конкретный способ сети.
В приложении передаю UnsplashPhotoService, в тестах — управляемую подмену».

**9. Зачем две ViewModel и один экран сетки?**

«Разметка и действия коллекции одинаковы, но источники разные: API и избранное.
PhotoGridViewModel позволяет использовать один ViewController без копирования интерфейса».

**10. Общее избранное — singleton?**

«Нет глобального shared. Coordinator создаёт один Store и передаёт его нужным объектам.
В тесте можно создать другой независимый Store».

### О UIKit и навигации

**11. Чем UIView отличается от UIViewController?**

«UIView представляет часть интерфейса. UIViewController управляет своей View,
её жизненным циклом и взаимодействиями. Он может содержать другие контроллеры».

**12. Когда вызывается viewDidLoad?**

«После загрузки View контроллера. Это место первоначальной настройки.
Возврат к существующему экрану не означает новый viewDidLoad».

**13. Почему для картинок страницы используется viewWillAppear?**

«Страница может появляться повторно после свайпа. Если картинки нет,
при появлении запускаем загрузку; после исчезновения отменяем ожидающую задачу страницы».

**14. Для чего dataSource, delegate и layout?**

«DataSource предоставляет элементы, delegate сообщает о взаимодействиях,
layout определяет расположение. В галерее первые два реализует ViewController,
а layout создаётся в GalleryLayout».

**15. Почему UICollectionView, а не много UIImageView в UIStackView?**

«Коллекция переиспользует ячейки и предназначена для длинных прокручиваемых списков и сеток.
Создавать отдельную View для каждой фотографии всей ленты было бы дороже».

**16. Что такое IndexPath и чем он отличается от id?**

«IndexPath — позиция в коллекции: секция и элемент. id принадлежит самой фотографии.
Позиция может измениться при обновлении массива, поэтому сохранение и проверка избранного используют id».

**17. Зачем translatesAutoresizingMaskIntoConstraints=false?**

«Я задаю ограничения сама. Отключаю преобразование autoresizing mask,
чтобы оно не добавляло лишние ограничения к моей программной разметке».

**18. Как поддерживаются повороты?**

«Экран связан ограничениями с контейнером, а число колонок вычисляется из ширины layout environment.
В просмотре описание можно прокручивать вертикально». Назови проверенные устройства,
не обещай проверку каждого размера.

**19. Почему используется push, а не present?**

«Просмотр — следующий уровень внутри выбранной вкладки. NavigationController
даёт стек и стандартный возврат назад. Модальное представление больше подходит для отдельного временного сценария».

**20. Зачем каждой вкладке свой NavigationController?**

«У вкладок независимые стеки. Открытый просмотр в галерее не должен становиться
общим стеком для избранного». При переключении вкладки UIKit может сохранять её ранее открытый экран.

**21. Как работают свайпы и почему индекс не меняется в начале жеста?**

«UIPageViewController запрашивает соседние страницы. Индекс обновляю после подтверждённого
завершения перехода: начатый свайп пользователь может отменить».

### О сети и изображениях

**22. Что такое endpoint и какой используется?**

«Endpoint — адрес операции API. Здесь GET /photos с page и per_page=30».
URL изображений приходит в ответе и используется отдельными запросами.

**23. Как данные превращаются в модели?**

«После проверки HTTP-ответа JSONDecoder декодирует Data в массив Photo.
CodingKeys связывает alt_description с altDescription».

**24. Почему описания optional?**

«API может вернуть null или не предоставить описание. Код выбирает первую непустую строку
из description и altDescription, иначе показывает “Без описания”».

**25. Почему try await URLSession недостаточно для проверки успеха?**

«Транспортный запрос может успешно получить ответ с HTTP 401 или 500.
Поэтому отдельно проверяю statusCode перед декодированием данных».

**26. Где находится ключ и почему не в URL?**

«Он читается из локального Secrets.plist и передаётся заголовком Authorization.
Не хранится в исходниках и Git. Но из установленного приложения ключ можно извлечь —
это ограничение прямого клиентского подключения».

**27. Как запускается следующая страница?**

«Когда willDisplay сообщает об одном из последних шести элементов,
экран просит ViewModel.loadNextPage. ViewModel проверяет состояние и выбирает номер страницы».

**28. Как защищены повторные запросы?**

«isLoading устанавливается до первого await. Следующий вызов видит его и выходит.
После ошибки автоматическая подгрузка также не повторяется бесконечно: нужен явный повтор».

**29. Что произойдёт при ошибке второй страницы?**

«Первая останется на экране, nextPage не изменится. Повтор запросит вторую страницу ещё раз».

**30. Как отличается refresh?**

«Он запрашивает страницу 1 и заменяет список после успеха.
Если обновление не удалось, старые данные сохраняются, а повтор снова обращается к первой странице».

**31. Зачем дедупликация по id?**

«Страницы изменяемой ленты могут пересечься. Set известных id не позволяет
показать одну фотографию дважды при добавлении ответа».

**32. Почему картинки не путаются при прокрутке?**

«При настройке и переиспользовании отменяется старая задача. После ожидания
проверяются отмена и id. Запоздавший результат для другого фото не устанавливается в ячейку».

**33. Зачем два кеша?**

«NSCache хранит подготовленные UIImage, URLCache — HTTP-ответы.
Первый ускоряет повторный показ, второй может сократить повторные сетевые загрузки».

**34. Почему один URL не скачивается одновременно несколько раз?**

«ImageLoader хранит словарь незавершённых Task по URL.
Следующий потребитель ожидает уже существующую Task, а не создаёт второй запрос».

**35. Работает ли приложение полностью без сети?**

«Нет. Метаданные избранного сохранены локально, а доступность картинки зависит от кеша.
Для новой ленты и отсутствующих в кеше изображений нужна сеть».

### Об избранном и Core Data

**36. Зачем Store, если уже есть Repository?**

«Repository знает, как читать и сохранять Core Data. Store хранит единое состояние
для экранов, управляет операциями и уведомляет ViewModel. Их ответственности различаются».

**37. Как синхронизируется сердечко?**

«Все ViewModel используют один Store. После успешного сохранения он обновляет
массив и уведомляет наблюдателей, а ViewModel вызывают onChange своих экранов».

**38. Что будет, если save завершится ошибкой?**

«Repository откатывает несохранённые изменения контекста. Store оставляет прежний список,
показывает ошибку и запоминает фотографию для повтора».

**39. Почему сердечко обновляется после записи, а не заранее?**

«Так интерфейс не выдаёт неудавшуюся запись за сохранённый выбор.
Оптимистичное обновление потребовало бы продуманного отката, его здесь нет».

**40. Где файл модели Core Data?**

«Модель создаётся программно в makeModel. В ней Favourite с id, payload и addedAt.
xcdatamodeld не обязателен, когда NSManagedObjectModel передаётся контейнеру напрямую».

**41. Что такое context?**

«Рабочая область Core Data для выборки и изменения объектов. Изменить объект
в контексте недостаточно: для постоянной записи вызывается save».

**42. Где хранятся сами фотографии?**

«Core Data хранит метаданные и URL. Двоичные изображения обслуживает ImageLoader и его кеши».
Не называй JSON payload изображением: это описание Photo, а не JPEG.

**43. Почему избранное сохраняется после перезапуска?**

«SQLite-файл остаётся в контейнере установленного приложения.
При новом запуске создаётся новый Store и читает сохранённые записи».

**44. Почему при удалении из просмотра фотография не исчезает сразу?**

«Просмотр использует снимок списка для стабильных индексов во время свайпов.
Сердечко обновляется, а после возврата удалённого фото в избранном нет».

### О Swift, тестах и процессе

**45. Task автоматически выполняется в фоне?**

«Нет. Важно, в каком контексте она создана. Task внутри MainActor может наследовать
его изоляцию. await приостанавливает ожидание, но не переносит произвольный тяжёлый код в фон».

**46. Зачем MainActor, если есть isLoading?**

«MainActor организует доступ к состоянию, а isLoading защищает логическую операцию
через точки await. Один инструмент не заменяет другой».

**47. Почему нужен weak self?**

«Контроллер хранит ViewModel, она хранит замыкание. Сильный захват контроллера
в замыкании может замкнуть цикл. Weak-ссылка не удерживает закрытый экран».

**48. Почему нельзя сделать все ссылки weak?**

«Кто-то должен владеть объектами. Например, SceneDelegate удерживает Coordinator.
Если все владельцы исчезнут, объект освободится раньше, чем нужен».

**49. Чем тесты отличаются от ручного запуска?**

«Тесты воспроизводимо проверяют выбранные правила и ошибки. Ручной запуск показывает,
как работают настоящие жесты и раскладка. Оба вида проверки нужны».

**50. Как тестируется сеть без интернета?**

«ViewModel получает подменный сервис, а конкретный сетевой сервис проверяется
через тестовый URLProtocol с заданными ответами».

**51. Как проверить два запроса одновременно без нестабильного sleep?**

«Подмена удерживает первый ответ на continuation. Тест дожидается начала запроса,
вызывает второй и проверяет счётчик, затем вручную завершает первый».

**52. Что доказывает тест SQLite?**

«Новая Repository читает ранее сохранённую запись из того же временного файла,
повторное добавление не создаёт дубль, удаление сохраняется. Перезапуск приложения
проверяли отдельно в симуляторе».

**53. Сколько тестов и что важнее числа?**

«22 unit-теста и один UI-тест. Важнее сценарии: ошибка и повтор страницы,
перекрывающиеся запросы, отмена, кеш, сохранение и синхронизация избранного».

**54. Что проверяет SwiftLint?**

«Правила стиля и некоторые нежелательные конструкции. Он не проверяет,
что сердечко действительно сохранилось, и не заменяет тесты».

**55. Для чего PR?**

«Чтобы изменения отдельной ветки можно было посмотреть, обсудить и проверить
перед включением в main. PR и merge — разные действия».

**56. Какой баг был найден и исправлен?**

«Регистрация ячейки была lazy и создавалась слишком поздно при первом получении ячейки.
Её инициализацию перенесли в настройку коллекции и добавили тест создания первой ячейки».
Это хороший пример ответа с конкретной причиной, исправлением и регрессионной проверкой.

**57. Что было бы первым следующим улучшением?**

Выбери одно и обоснуй: проверка на минимальной ОС и iPad; доступность; измерение
производительности; фоновые операции Core Data для большого избранного.
Не перечисляй десять технологий, если не можешь объяснить, какую проблему решает каждая.

**58. Что ты сделаешь, если не знаешь ответ?**

«Точно знаю, что в моём коде происходит вот это. Деталь API сейчас не помню;
проверила бы документацию и небольшой воспроизводимый пример».
Это лучше выдуманного уверенного объяснения.

<a id="part-26"></a>
## 26. Сложные вопросы и честные ограничения

### «Ты уверена, что на iOS 17 всё работает?»

Сборка настроена на iOS 17+, но фактический финальный прогон был на iOS 27.2.
Правильный ответ: «Минимальная версия задана, а запуск на минимальной ОС ещё нужно проверить».
Deployment target не заменяет тестирование runtime-поведения.

### «Здесь вся обработка в фоне?»

Нет. URLSession асинхронно выполняет сетевую работу, однако многие объекты изолированы
MainActor, а Repository использует viewContext. Для небольших ответов это простое решение.
Тяжёлые выборки, декодирование больших объёмов и обработку изображений следует измерять
и при необходимости менять архитектуру исполнения.

### «Почему Core Data хранит JSON, а не отдельные поля?»

Это упрощение для восстановления целого Photo без сложного поиска по его полям.
id и дата доступны отдельно. Недостатки — слабее типизация payload, сложнее предикаты
по автору и зависимость декодирования от структуры модели. При расширении требований
можно выделить атрибуты и продумать миграцию существующих записей.

### «У тебя есть полноценный offline-first?»

Нет. Offline-first означал бы существенно более полную стратегию локальных данных,
загрузок, обновления и конфликтов. Здесь локально сохраняется выбор пользователя,
а картинки могут зависеть от сети. Так и написано в README.

### «Почему не Diffable Data Source?»

Для одной простой секции достаточно обычного dataSource: добавления в конец обрабатываются
insertItems, замены и удаления — reloadData. Diffable Data Source мог бы упростить
более сложные обновления и анимации, но это возможное улучшение, не текущая реализация.

### «Почему нет полноценного prefetching?»

Следующая страница запрашивается заранее через willDisplay последних элементов.
Это не UICollectionViewDataSourcePrefetching для предварительной загрузки каждой картинки.
Вводить его стоит с измерением пользы и управлением отменой, а не ради наличия ещё одного протокола.

### «А если загрузить тысячи фотографий?»

Кеш может освобождать изображения, но массив метаданных галереи растёт по мере пагинации.
Избранное также читается целиком. Возможные улучшения: ограниченное окно данных,
порционные выборки, индекс id для ускорения contains, фоновый context и измерения памяти.
Это не означает, что текущий небольшой сценарий сломан; это граница масштабирования.

### «Почему описание или подпись могут занимать много места?»

Описание приходит от API и может быть длинным. В просмотре предусмотрена вертикальная
прокрутка. В ячейке подпись ограничена двумя строками и фиксированной дополнительной
высотой. На очень больших размерах шрифта это следует отдельно проверить и доработать.

### «Можно ли безопасно скрыть ключ в приложении?»

Нельзя обещать абсолютную секретность ключа, который должен использовать клиент.
Локальный plist предотвращает попадание в Git, но не извлечение из приложения.
Для публичного продукта потребуется отдельное решение доступа с серверной частью,
лимитами и контролем использования. Сейчас это учебное прямое подключение.

### «Никаких утечек и всегда 60 FPS?»

Такой результат не измерялся. Корректно назвать принятые меры — weak-ссылки,
переиспользование, кеш, подготовку уменьшенных изображений — и обозначить необходимость
Instruments. Не выдавай отсутствие видимого сбоя за количественную гарантию.

### «Все ошибки покрыты?»

Покрыты конкретные сценарии, перечисленные в тестах. Не проверены все возможные
сочетания сетевых сбоев, нехватки диска, повреждения данных, размеров экрана и действий
пользователя. Зелёные тесты снижают риск регрессий, но не устраняют необходимость ревью.

### «Какие утверждения нельзя говорить на защите?»

- «await всегда переносит код в фон».
- «Core Data и NSCache — одно и то же».
- «Access Key защищён Keychain» — Keychain здесь нет.
- «Сердечко ставит лайк в аккаунте Unsplash» — избранное локальное.
- «Изображения записаны в Core Data» — там метаданные.
- «Есть бесконечная подгрузка в просмотре» — листается снимок загруженного списка.
- «В приложении Combine / SwiftUI Observation / Diffable Data Source» — они не используются.
- «Проверено на всех iPhone и iPad» — такого прогона не было.
- «100% покрытия и гарантированное отсутствие утечек» — таких доказательств нет.
- «cancel мгновенно убивает всю связанную сетевую работу» — отмена кооперативна, задачи разделены.

а не научиться менять проверку до зелёного результата любой ценой.

### Упражнение 6. Проследить сердечко

Поставь breakpoints в Store.toggle, Repository.setFavourite и favouritesDidChange
одной ViewModel. Нажми сердечко. Заметь, что массив Store меняется после успешного
ожидания репозитория, а затем приходят уведомления.

Объясни, почему экран не обращается напрямую к NSManagedObjectContext.

### Упражнение 7. Проверить сохранение

Добавь одно фото, останови приложение кнопкой Stop и запусти снова через ⌘R.
Убедись, что оно осталось в избранном. Удали и повтори запуск.
Не удаляй само приложение между шагами: это уже другой сценарий.

### Упражнение 8. Отменить свайп

Открой фото, начни движение к следующему и верни палец назад.
Проверь, что номер и сердечко относятся к оставшейся странице.
Найди guard completed в delegate и объясни его роль.

### Упражнение 9. Сделать маленькое изменение

В учебной ветке измени отступ сетки или текст пустого состояния.
Перед изменением назови файл и слой ответственности. После изменения проверь
portrait и landscape, посмотри diff и убедись, что не изменились несвязанные файлы.
Не меняй per_page=30 в сдаваемой версии — это требование задания.

### Упражнение 10. Добавить тест самостоятельно

Возможный сценарий: после успешного чтения избранного последующее чтение падает,
а уже известный список остаётся. Или проверь, что ошибка сервиса 500 отображается
как server(500). Сначала сформулируй ожидаемое поведение, затем подмену и проверку.
Если не можешь назвать ошибку, которую тест поймает, возможно, тест не нужен.

### Как искать проблему по симптому

**Приложение не собирается.** Сначала первая ошибка в Issue Navigator и Build Log.
Не начинай с удаления DerivedData, если сообщение указывает на конкретную строку Swift.

**Сборка прошла, но запуск не удался.** Проверь выбранное устройство, runtime,
signing для физического телефона и сообщение Xcode. Это ещё не ошибка API.

**Пустая галерея с ошибкой ключа.** Проверь наличие локального файла, имя поля,
отсутствие placeholder, затем пересобери. Не публикуй сам ключ.

**Фото не грузятся, но авторы видны.** JSON уже получен; исследуй ImageLoader
и конкретный URL картинки, а не только List Photos.

**Список застыл со спиннером.** Проверь, доходит ли задача до завершения,
снимается ли isLoading, выполняется ли defer и вызывается ли onChange.

**Неверная картинка в ячейке.** Проверь отмену, очистку в prepareForReuse и соответствие id.

**Сердечко не синхронизируется.** Проверь, что ViewModel получили один экземпляр Store,
зарегистрировались как наблюдатели и вызывают onChange после notify.

**Избранное исчезло после запуска.** Уточни, не удалялось ли приложение,
используется ли тот же симулятор и bundle, завершился ли save и не показана ли ошибка чтения.

**Auto Layout пишет конфликт constraints.** Посмотри список конфликтующих ограничений,
наличие translatesAutoresizingMaskIntoConstraints=false и полноту связей по каждой оси.
Один только визуально приемлемый экран не доказывает отсутствие конфликтов в консоли.

### Что полезно открыть в Xcode

- Project Navigator — найти файл и его место в проекте.
- Issue Navigator — ошибки сборки и предупреждения.
- Test Navigator — выбрать конкретный тест или набор.

источником остаётся текущий исходный код, а не чужой пример с другой архитектурой.

### Пять цепочек, которые стоит помнить

```text
Запуск:
AppDelegate → SceneDelegate → UIWindow → AppCoordinator → вкладки и экраны

Страница:
View → GalleryViewModel → PhotoServicing → URLSession → PhotoPage → onChange → render

Картинка:
PhotoCell → ImageLoading → кеш / общая Task → UIImage → проверка отмены и id → UIImageView

Открытие:
didSelectItemAt → onSelectPhoto → Coordinator → DetailsViewModel + DetailsViewController → push

Сердечко:
View → ViewModel → Store → Repository → Core Data save → состояние Store → наблюдатели → View
```

### Короткий словарь

**State** — текущее состояние: данные, загрузка, ошибка, выбор.
**Callback** — переданная функция, вызываемая при событии или результате.
**Delegate** — объект, которому передают обработку определённых событий.
**Dependency** — объект, без которого другой объект не выполнит свою работу.
**Repository** — слой доступа к данным хранения.
**Persistence** — сохранение данных между запусками.
**Snapshot** — снимок набора данных на конкретный момент.
**Reuse** — повторное использование объекта ячейки для другого элемента.
**Race** — ситуация, когда результат зависит от порядка пересекающихся операций.
**Cancellation** — запрос отмены, который работа должна учитывать.
**Retain cycle** — цикл сильных ссылок, мешающий освобождению объектов.
**Regression** — поломка ранее работающего поведения после изменения.
**Stub** — подмена с заранее заданным поведением для проверки.
**Baseline** — зафиксированный набор существующих замечаний, относительно которого проверяются новые.

### Как отвечать, когда волнуешься

Используй три предложения: «Что происходит», «Где это в коде», «Почему так».
Например: «После сохранения сердечко обновляется на всех экранах.
Это делает FavouritesStore через наблюдателей ViewModel.
Так экраны не ведут независимые списки и не расходятся по состоянию».

Не нужно помнить все детали наизусть. Нужно понимать связи и уметь доказать
объяснение конкретным кодом, тестом или наблюдаемым действием приложения.
